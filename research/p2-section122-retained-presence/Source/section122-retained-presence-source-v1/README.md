This packet is an unexecuted Source proposal. It has not been imported, tested,

## Actual product change

A valid JSON string such as `"false"` was truthy at the old retained `held` and
`present` gates. Numbers, lists and objects could also become automatic
possession or membership claims. This proposal uses the exact bool as its
software qualification; absent flags retain the proven historical `True`
default. A non-bool is unknown, including values that happen to be falsy.
The raw record and original file are kept. Unknown records are excluded from
automatic holdings, current roster, cultivation, personal buffs, historical
counter reuse and negative recipient-evidence lifecycle consumers. Inventory
cannot become complete solely because all unknown records were omitted.

This is an application evidence policy. RFC 8259 permits strings, numbers,
arrays, objects and null as JSON values; it does not require this application's
fields to be bool. Python's official decoder table establishes their different
native types. Reused original downloaded documents, hash-checked bytes,
source quotes and download ledgers are in `public-sources/`; no new download or
game-mechanic discovery is claimed.

## Retention and fresh evidence

Read-only views do not write the file, coerce flags, remove raw records, or
repair them. Legacy signature migration and saved icon-memory replay cannot
override an unknown held flag. Metadata-only reads, including unqualified
owned-card candidates, preserve suspended icon memory without replaying it.
A genuine new held bar/card/ID observation uses the existing recognition
contract to qualify True; a fully identified inventory or explicit empty bar
uses the existing contract to qualify False. An exact bool control follows the
old confirmation/loss rules. An unknown prior value uses the separate
`state_flag_reconfirmed` history event, retaining `previous_value` and the
entire `previous_record`, rather than inventing acquisition or loss events.

For operators, an observed identity qualifies presence but cannot reconfirm
old cultivation, recruitment source, progress or personal buffs. Existing
`invalid_fields` and `invalid_skill_ranks` retain and mask old cultivation.
Only the corresponding explicitly observed fields/ranks are removed from the
mask. `unconfirmed_run_metadata` masks retained source, advanced and recipient
metadata. Its exact fresh entry points are:

* Non-null `recruitment_kind` in the current operator observation qualifies
  that source only; it does not qualify personal buffs or fabricate an old
  recruitment transition.
* An explicitly observed `advanced` field qualifies that field only.
* A partial current popup qualifies only its visible `char_buff_ids`, kept in
  `qualified_char_buff_ids`. Old raw positives remain stored but do not revive.
* A fresh complete popup with an explicit ID list qualifies the recipient
  group and uses the original full-popup replacement rules.

The mask survives saving, reloading and later identity-only pages. Subsequent
origin, elite or advanced pages cannot use still masked old values as event
baselines. Existing origin-discovery repair and recipient absence invalidation
cannot consume masked metadata. Raw cultivation display, automatic overview,
manual account preview, current-run metadata and direct personal-buff display
use the same qualification. Healthy metadata continues to return the original
member reference and preserve its existing label text.

Unknown held-counter proof remains in raw resources. A qualification event
adds an evidence cutoff for both True and False, so an old proof cannot revive
through unknown -> False -> True. A fresh verified counter in the qualification
packet is allowed at the same timestamp. This is proof qualification; it does
not assert a game reset, layer loss, probability, grant or reacquisition rule.
Gold and parts keep the old rules. The independent legacy
`inventory_verified` numeric/None short-circuit types also remain unchanged.
