## 已闭合的缺口

公开第63节 `validation-after61/draft63.json.gz` 的真实 `records[id=389]` 输入为深海色 S1、等级10、所选2只触手、10秒观察窗口，完整结果同时有：

- `触手数量 2；技能生命回复 4200，生命回复不计直接治疗。`
- `触手数量 2；技能生命回复 1400，生命回复不计直接治疗。`

二者是旧实现分别用名义持续参数30秒和截断观察10秒，乘每只基础回复70/秒及所选数量2得到的**不同算术参考**。它们没有相应范围标签，也没有“基础倍率”标签。不能把其中一条称为错误数值，也不能相加。复制的完整 row 与原完整公开 gzip 都在包中；原结果调用来自旧回执，本次重放0。

当前 `operator_engine.py` 的同一 S1 分支仍先把这类基础总量字符串加入 `self.notes`。`calculate()` 先生成完整计划，再生成观察计划，并通过 `dict.fromkeys` 去重后放进 `estimate.notes`；不同数值无法去重。`relics.finish()` 在这之后确定 `relic_regeneration_multiplier`，不会改写上述字符串。`build_report()` 的深海色回复速度却明确采用这个乘数，`format_report()` 继续显示原 `estimate.notes`。精确创建、合并、finish 和呈现路径见 `source-contract-paths.json`。

单个已接入活玫瑰 `rogue_6_relic_legacy_81` 的公开资料给“所有我方单位受到的治疗和生命回复效果+20%”，固定回复原黑板选择器为 `hp_recovery_per_sec[mul]`，值 `.2`，现有离线规则为 `regeneration_factor=1.2`。由当前代码可静态推出：同样 S1 参考中，回复速度采用84/秒及合计168/秒，原 note 的4200/1400仍为未加倍率的基础值。**这部分是静态代码路径预测，不是新的玫瑰实际 API 复现**；旧389没有玫瑰。缺口是未区分基础参考与含倍率速度，不能据此宣称真实回复量应为5040/1680。

## 最小可实施范围

建议只修 `operator_engine.py` 的深海色 S1 note 和 `reporting.py` 深海色 S1 回复块的资格说明，并增加小范围回归。保留当前基础算术数值、基础70/秒、名义30秒和所选数量等有用信息，给两次计划明确身份：

- 完整计划：**基础回复的名义持续参数参考**，标明30秒、所选数量和“未计生命回复效果倍率”。
- 观察计划：**基础回复在本次截断观察范围内的连续覆盖假设参考**，标明实际使用的参考时长，例如10秒；同样标明未计倍率。窗口超过名义持续时只采用已有截断，不扩展技能；0秒参考为0。
- 生命回复块仍沿用已经实现的含倍率每只/合计速度，清楚说明速度与上面的基础参考口径不同。回复速度在零观察/无敌方供靶时继续保留为条件参考，不被置零。
- 明示真实触手在场、技能回复首跳/结束以及实际总回复尚未核验；生命回复独立于直接治疗 HPS。不增加真实回复总量、事件、组件或有效治疗，也不改变伤害、HP组合层、模组/数量门槛、S2、普攻或充能阶段。

阶段限定为 S1 计划的技能阶段：`not normal and self.n==1`。普通攻击/充能计划没有这个 S1 回复 note。观察参考的时长沿用已有 `min(名义技能持续, 所选窗口)`，这是该工具当前连续速率算术口径，不能认证 native 持续覆盖。默认窗口或相同参考时长应保持可读，不产生两个同名无范围的总量。

采用这种方案可以保留两项算术信息，同时明确来源、范围和倍率。若后续希望展示含倍率的条件总量，应另行设计结构化资格信息并审批验证预算；本候选不新增这种输出或真实时钟。
