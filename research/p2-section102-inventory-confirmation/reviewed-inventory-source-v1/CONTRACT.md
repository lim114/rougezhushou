# Future102 inventory confirmation consumer boundary — Source only

This proposal has not been applied or executed. It does not complete Section102.

## Evidence and limited compatibility policy

The current RunState directly produces only native bool: reset writes False;
changed inventory revokes the claim with False; a complete identified current or
valid historical held bar, or explicit zero, writes True. Saved JSON is accepted
and merged without rewriting inventory_verified. Public research/verification
JSON scan found 122 direct keys across 61 matched parsed files, all bool, with no
skipped files; this is a public archived-fixture scope, not every user save or a
game native schema. The copied Root actual original receipt separately proves
accepted count0 flags True, False, None, 'false', [1], int1 and int0, byte-preserved
disk, absent tmp. The original status falsely confirms 'false' and [1].

The proposed helper rejects native JSON text/array/object flags at the three
claim consumers; it leaves native bool/int/float/None unchanged as input to the
original short-circuit expressions. Therefore None remains native None in
complete, int0 remains int0, int1 yields the same bool True only when original
count/known arithmetic also holds. Other numeric JSON flags are compatibility
preservation, not newly validated game or producer facts. Numeric edge controls
(including signed float zero) still require Root actual testing. A bool-only
schema/loader rejection would regress the actually accepted int1 and None
contracts and discard siblings, so it is not proposed.

Inventory counts and timestamps, held records, unknown extras, bar evidence,
relic/character data and save/protection policy are untouched. No normalization,
cache migration, rejection or automatic persistence occurs merely to qualify a
flag. Raw anomalous flag remains in memory and disk; view/status qualification
is separate. Legitimate current full reading may subsequently overwrite it with
bool True through the original producer, or a genuine changed inventory may
write bool False. This is evidence evolution, not string parsing or repair.

## Minimal implementation and limits

One small module helper plus the three consumer expressions change: prior claim
used for displaced full inventory, claim used for new positive records, and
inventory_status. Consumer consistency prevents the same anomalous flag from
claiming both a completed view and a previously verified inventory change.
Direct bool-producing assignments remain byte-identical. Current callable
count/removal predicates and JSON codec remain unchanged.

This boundary does not qualify complete_bar, held, other confirmed fields, native
clocks, task unlocking, unknown numeric evidence or the whole run-state schema.
The candidate must be rebased only if the baseline RunState hash has drifted;
Source parse is not execution and must not be reported as a test PASS.

## Required actual validation

Root must execute the proposed original-API temporary-state tests freshly after
Source review, along with existing inventory snapshot/reading/grade/tool,
run-state reliability and persistence regressions. Preserve the original
anomalous-flag receipt; it is defect evidence, not a PASS. Each trial records real
exit and checks Source guard.

Use real MainWindow with owned temporary settings/account/run state, existing
DesktopBackend boundary and genuine calculate_damage. Compare healthy native
math and all three format texts gold/candidate, including bool/int/None controls.
For malformed claims, assert the new incomplete notice/qualification while
keeping known holdings, actual count values/types, calculation numeric fields,
caller input, account state and original disk bytes. Test close/reopen with no
new reading (raw flag preserved and still incomplete), then a legal complete
zero and complete relic+tool read (bool True, original confirmation timestamp,
actual save/restart). Check stale/cross-run and partial evidence cannot upgrade.
No fake producer, whole-module skip, fake successful IO or undocumented game
mechanism may replace these runtime assertions.
